# Strings and translations

How a user-visible string is written in Weasis 5, what the build checks, and how the translations
reach the application.
The translations themselves live on Transifex (project `weasis-5`) and are built by the `5.0`
branch of the [weasis-i18n](https://github.com/nroduit/weasis-i18n) repository as
`weasis-i18n-dist-5.0.0-SNAPSHOT`, the package named by `i18n.version` in `weasis-parent/pom.xml`
(`master` keeps `4.0.0-SNAPSHOT` for Weasis 4); this page is about the English sources in this
repository.

## Where a string lives

Every user-facing module has a `Messages` class next to a `messages.properties` file in
`src/main/java`.
A string never appears as a literal in the code: a label is `Messages.getString("Class.key")`,
a sentence with values is `Messages.format("Class.key", a, b)`, and a word every module shares is
`Messages.common("cancel")`.

| Call | What it reads | Example |
| --- | --- | --- |
| `Messages.getString(key)` | the string of this module, `!key!` when missing | `Messages.getString("PrintDialog.print")` |
| `Messages.format(key, args…)` | the string with its `{0}` arguments filled by `MessageFormat` | `Messages.format("PrintDialog.page_of", page, count)` |
| `Messages.common(key)` | the `common.*` section of weasis-core | `Messages.common("cancel")` |

The `Messages` classes delegate to `org.weasis.core.api.util.Bundles`; the launcher, which does not
see weasis-core, has its own copy.
A translation reaches a plugin through its class loader: the launcher publishes the
`<module>-i18n` packages on the shared library loader, so `ResourceBundle` finds
`messages_<lang>.properties` by parent delegation (`Translations`).

## Writing a key

- **One key, one meaning.** When the same English word means two things (*Open* the verb, *Open*
  the state), write two keys and two notes.
  Never reuse a key of another class.
- **Common words once.** Cancel, Close, Delete, Series, Study, Image, None, Apply… are defined in the
  `common.*` section of `weasis-core/messages.properties` and read with `Messages.common`.
  A module key that repeats a common word is reported by the build; keep it only where the common
  word does not fit (an overlay corner, an action label, a measurement name).
- **Arguments with `MessageFormat`.** Write `{0}`, never `%s`; a number that must not take a
  grouping separator (a port, a texture size) is `{0,number,#}`, a decimal is `{1,number,0.00}`.
  In a string that contains `{`, an apostrophe is written twice: `l''image`.
  No sentence is assembled from parts, and HTML stays minimal.
- **A developer note above every ambiguous key.** Transifex shows the comment line above a key
  as the string's developer note.
  The build requires one on a one-word string, on a string with arguments (saying what each `{n}`
  is) and on a string with a character limit; write one for anything else that is unclear out of
  context (a menu item or a tooltip, a verb or a noun).
- **A character limit where the slot cannot grow.** `# max:N` on the note line: tool tab titles 24,
  column headers 20, buttons 28, action labels 32, overlay corner texts 18, status lines 64.
  Menus, tooltips and dialogs grow with their text and take no limit.

```properties
# max:28 Button of the print dialog (verb)
PrintDialog.print=Print
# Page counter of the print preview and the page footer; {0} = the page number, {1} = the number of pages
PrintDialog.page_of=Page {0} / {1}
```

- **UTF-8, real characters.** Write `…`, `°`, `µ`, `—` as they are, never `\u2026`: since Java 9 a
  resource bundle reads UTF-8, and the files, the diffs and the notes stay readable.
  An escape is kept only for a character that cannot be seen (a non-breaking space, a zero-width joiner).
  In IntelliJ, set the encoding of properties files to UTF-8 and turn off *Transparent native-to-ascii
  conversion*, otherwise the IDE writes the escapes back.
- **No obsolete key.** A key the code no longer asks for fails the build; a key the code asks for
  and no bundle has fails it too.
  A key built at run time from a prefix (`"TagCategory." + name`) is recognized by its prefix.
- The command surface (verb names, options, help, error bodies), the logs and `weasis:info` are
  English only, by decision; DICOM defined terms shown as data are shown as received.

## The checks

`tests/src/test/java/org/weasis/tests/i18n/I18nSourcesTest` runs with the build on every
`messages.properties` of the repository and fails on: an invalid `MessageFormat` pattern or a lone
apostrophe in one, a `printf` placeholder, a key asked for by the code that no bundle has, an
unused key, an ambiguous string without a note, a hard-coded label in the Swing code (`setText("…")`,
`new JButton("…")` without `// NON-NLS`), an English text longer than its own `max`, a file that is not
UTF-8 or that escapes a printable character as `\uXXXX`.
It prints the common words repeated in the modules.

`TranslationChecks` holds the rules that apply to a translation against its English source
(same arguments, valid pattern, length within `max`, no key absent from the source) and runs as a
single-file program on any directory of `messages*.properties`:

```bash
java tests/src/test/java/org/weasis/tests/i18n/TranslationChecks.java weasis-core/src/main/java
```

The weasis-i18n build runs its own copy on the downloaded translations: each module drops the
translations that break a rule (`--drop`, the key then shows English), then the package is checked.
That copy also reads ISO-8859-1, the encoding Transifex delivers for the 4.x resources.

## The pseudo-locale

Start Weasis with `-Dlocale.lang.code=en-XA` (or set `locale.lang.code` to `en-XA` in the
preferences file) and every translated string shows accented, framed and lengthened:
`[Çåñçél~~]`.
A plain English word on screen is a hard-coded string; a frame cut on the right is a label whose
slot cannot take a longer translation.
The pseudo-locale is derived at run time from the English base (`PseudoLocale` in the launcher),
so no translation package is fetched for it.
